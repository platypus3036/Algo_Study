# 📝 251118 스터디 회고

## 🎯 이번 주 스터디 목표 및 주요 학습 내용
- 해시/맵, 집합, 조합 사전 계산, 이분 탐색 등 코딩테스트에서 자주 등장하는 자료구조·전처리 패턴 복습
- 구현량이 있는 시뮬레이션 문제에서도 규칙을 먼저 수식/좌표 관점으로 정리한 뒤 코드로 옮기는 연습

## 📚 문제별 토론 및 회고

### 📝 신고 결과 받기
- **문제 유형/출처**:  Level 1
- **주요 접근법 요약**:  
  - `defaultdict`(또는 `dict`)를 이용해서, key에 피신고자 id를 두고 value에 신고한 사람 id들을 넣어 관리했다.  
  - 신고 내역을 우선 리스트에 모은 뒤 `set`으로 변환해 동일 신고자→피신고자 쌍 중복을 제거하고, 이후 각 피신고자마다 신고자 수를 세어 정지 대상과 메일 발송 대상을 계산했다.  
  - Map/dict를 2개 사용해 “신고자 → 신고한 사람 목록”과 “피신고자 → 신고자 집합”을 분리 저장해, 최종적으로 메일 횟수를 손쉽게 구할 수 있도록 구조를 설계했다.
- **토론 내용 및 피드백**:  
  - 문자열 파싱/중복 제거/집계라는 전형적인 해시 문제라, 자료구조만 잘 잡으면 구현 난이도가 높지 않다는 점을 재확인했다.  
  - key–value를 어떻게 설계하느냐에 따라 코드 복잡도가 크게 달라지므로, 입출력 형식을 보고 먼저 자료구조 스케치를 해두자는 얘기를 나눴다.

### 📝 택배 상자 꺼내기
- **문제 유형/출처**: Level 1
- **주요 접근법 요약**:  
  - 총 상자가 몇 개 쌓여 있는지를 나타내는 2차원 리스트(층, 열)를 만든 뒤, 가로로 w개씩 지그재그(왼→오, 다음 층은 오→왼)로 번호를 채워 넣는 방식으로 시작했다.  
  - 특정 상자 번호 기준으로 “그 아래에 몇 층이 더 쌓여 있는지”만 알면, 그 차이로 꺼내야 할 상자 수를 구할 수 있다는 점을 이용했다.  
  - 밑에 쌓여 있는 층이 짝수층인지 홀수층인지에 따라 상자가 실제로 놓이는 열 위치가 달라지므로, 층 인덱스의 홀짝에 따라 `dir`을 바꾸며 상자 위치를 채우는 방식을 사용했다.  
  - 직접 상자들의 위치를 2중 리스트로 모두 구성한 후, 마지막에 목표 상자의 위치에서 아래쪽으로 역순 탐색을 하며 실제 상자가 존재하는 칸만 개수를 세도록 구현했다.  
  - 전체 그리드를 채운 뒤 n보다 큰 숫자가 들어갈 자리는 0(또는 `null`)로 채워 “빈 칸”을 표현했고, `arr[y][x]`에서 y를 행(층)으로 두어 방향 전환을 쉽게 했다.
- **토론 내용 및 피드백**:  
  - 지그재그 규칙을 직접 시뮬레이션하는 방식이라, 먼저 그림을 그리고 층/열 인덱스를 수식으로 정리한 뒤 구현하는 연습이 필요하다고 느꼈다.  
  - 빈 상자가 있으면 안 되기 때문에, 탐색 시 “해당 y가 범위 안인지, 그리고 실제 상자가 있는지”를 조건문으로 한 번 더 검증해 주는 방어 코드의 중요성을 다시 확인했다.

### 📝 순위 검색
- **문제 유형/출처**: Level 2
- **주요 접근법 요약**:  
  - info 최대 5만, query 최대 10만이라 단순 2중 for문으로 모두 비교하면 약 50억 번 연산이 되어 시간 초과가 확정이라는 점을 먼저 짚었다.  
  - 지원자가 지원 가능한 모든 경우의 수(언어 3, 직군 2, 경력 2, 음식 2 → 3×2×2×2=24)를 미리 만들어, 각 info 한 줄이 24개의 key(조합)에 매핑되도록 dict에 전처리하는 방식으로 설계했다.  
  - info를 그대로 매번 순회하는 대신, “모든 경우의 수에 대한 키값을 미리 만들어 dict에 리스트로 점수를 누적”해 두고, 쿼리 시에는 해당 키의 점수 리스트에서 이분 탐색으로 조건 이상인 지원자 수를 빠르게 계산했다.  
  - 조건 조합을 비트마스킹(예: `00 00 00 00`)처럼 숫자로 인코딩하는 방식도 아이디어로 떠올렸고, 결국 핵심은 “조합을 키로 한 전처리 + 정렬 + 이분 탐색”이라는 결론을 정리했다.
- **토론 내용 및 피드백**:  
  - 처음에 info와 query를 그대로 2중 루프로 비교하는 접근을 떠올렸다가, 입력 크기를 보고 바로 버려야 한다는 점을 다시 한 번 체감했다.  
  - dict에 미리 전처리해두고, 쿼리는 문자열 파싱 + 이분 탐색만 수행하도록 나누니, 시간 복잡도와 코드 구조 모두 깔끔해졌다는 점이 인상 깊었다.

## 🚀 KPT 회고 (Keep, Problem, Try)

### Keep (유지할 점)
- 입력 크기와 제한 시간을 먼저 보고, 가능한 시간 복잡도 범위를 감으로 잡은 뒤에 알고리즘/자료구조를 선택하던 습관은 계속 유지하기로 했다.  
- 문제마다 공통 패턴(해시/맵, 전처리 + 이분 탐색, 구현 시뮬레이션)을 말로 다시 설명하고, 각자 풀이를 비교하면서 차이점을 정리하던 리뷰 방식이 도움이 되었다.

### Problem (개선할 점)
- “전처리 후 빠르게 조회”가 필요한 문제에서, 처음에 2중 for문 직관적인 풀이에 너무 오래 머무는 경향이 있어, 입력 범위를 본 직후에 바로 배제하는 훈련이 더 필요했다.  
- 구현 문제(택배 상자 꺼내기 등)에서 규칙을 수식/좌표 단위로 먼저 정리하지 않고 곧장 코딩을 시작해, 인덱스 버그를 한두 번씩 꼭 내는 부분이 아쉬웠다.

### Try (다음에 시도할 점)
- 카카오/프로그래머스 기출 중 해시 + 전처리 + 이분 탐색 조합이 나오는 문제를 모아서, 순위 검색과 비슷한 패턴을 2~3문제 정도 더 풀어보기로 했다.  
- 구현 문제가 나오면 바로 코드로 가지 말고, 5분 정도는 그림과 좌표·공식 정리에만 투자한 뒤 템플릿화해서 구현하는 습관을 들여 보기로 했다.
